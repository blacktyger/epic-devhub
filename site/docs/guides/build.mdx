# Build the binaries

Three separate repositories produce the node, wallet and miner binaries.

| Binary | Repository | You need it for |
| --- | --- | --- |
| `epic` | <Repo name="node" /> | Validating and relaying the chain. Everything needs one |
| `epic-wallet` | <Repo name="wallet" /> | Keys, balances and building transfers |
| `epic-miner` | `EpicCash/epic-miner` | Producing blocks. Only for a local chain or actual mining |

If you would rather not build, [downloads](/downloads) lists the release archives.

## One prerequisite

Install [rustup](https://rustup.rs). Both Rust repositories pin their toolchain version in the
repository, so rustup selects the right one on its own. Do not pass a `+toolchain` or install a
specific version yourself.

That is the whole list on Linux and macOS. Both projects build on stock `ubuntu-latest` and
`macos-latest` CI runners with no additional system packages, so if a build fails there, suspect the
toolchain rather than a missing library.

## Windows needs two more things

Neither is mentioned in any upstream instruction, and both produce errors that do not name the real
cause.

**LLVM, for `libclang.dll`.** The `randomx` and `progpow` crates run `bindgen`, which loads
`libclang` at build time. The LLVM component in the Visual Studio "Desktop development with C++"
workload ships only `clang-format.exe` and `clang-tidy.exe`, so it does not satisfy this. Install LLVM
separately and point `LIBCLANG_PATH` at its `bin` directory.

**Windows SDK 10.0.20348 or later.** `croaring-sys` compiles with `-std:c11`, and MSVC's C11 mode needs
the UCRT `<stdalign.h>` that arrived in that SDK. With only an older SDK present the build stops with
`fatal error C1083: Cannot open include file: 'stdalign.h'`.

What you do **not** need on Windows, despite older Epic instructions listing them: `openssl` and
`strawberryperl` for the node and wallet. TLS goes through SChannel there, so `openssl-sys` is never
compiled. The miner is a different story, below.

## Node

```bash
git clone https://github.com/EpicCash/epic.git
cd epic
cargo build --release
```

The binary lands at `target/release/epic`.

Docker is an alternative if you want the node and nothing else:

```bash
docker build -t epic-mainnet -f etc/Dockerfile .
docker run -d --name epic-mainnet -p 3413:3413 -p 3414:3414 epic-mainnet
```

`docker compose up -d` also works, with one trap: `docker-compose.yml` maps chain data under
`./target/`, so a later `cargo clean` deletes a synced chain.

## Wallet

```bash
git clone https://github.com/EpicCash/epic-wallet.git
cd epic-wallet
cargo build --release
```

The binary lands at `target/release/epic-wallet`.

## Miner

The miner builds on Linux and macOS. `EpicCash/epic-miner` master is from September 2022 and its CI
covers Linux and macOS only.

On Linux and macOS, build it the same way as the others:

```bash
git clone --recursive https://github.com/EpicCash/epic-miner.git
cd epic-miner
cargo build --release
```

`--recursive` matters: the RandomX and ProgPow implementations are submodules.

:::note[Windows: build from the patched fork]

`EpicCash/epic-miner` master is from September 2022 and does not build on Windows with a current
toolchain. Four independent problems surface in sequence, from a dependency that no longer compiles to
a build script that writes unescaped backslashes into generated Rust.

Windows builds therefore come from
[blacktyger/epic-miner](https://github.com/blacktyger/epic-miner), which is upstream plus those four
fixes and nothing else. Every change is a candidate for upstream and this note goes away if they land.

```bash
git clone --recursive https://github.com/blacktyger/epic-miner.git
cd epic-miner
cargo build --release
```

`--recursive` is not optional here, and neither is cloning that fork rather than adding it as a remote
to an upstream checkout: `.gitmodules` uses relative submodule URLs, so the RandomX and ProgPow
submodules resolve against whichever repository you cloned. A clone of upstream pulls upstream's
submodules, including the RandomX crate that does not compile on Windows.

You also need [Strawberry Perl](https://strawberryperl.com) on `PATH`. The miner depends on `openssl`
with the `vendored` feature, so it compiles OpenSSL from source, and OpenSSL's `Configure` rejects the
msys perl that ships with Git for Windows.

Verified on 2026-08-24: a fresh `--recursive` clone of that fork plus `cargo build --release` produces a
working `epic-miner.exe` on `x86_64-pc-windows-msvc` with Rust 1.89.0, in about five minutes.

A stock Windows build mines RandomX only. No cuckoo plugins are built there, and ProgPow needs the
`opencl` or `cuda` feature.

:::

## Confirm you have three binaries

```bash
epic --version
epic-wallet --version
epic-miner --version
```

Put all three somewhere on your `PATH`, or note where they are. Both the node and the wallet resolve
configuration from the **current working directory** before falling back to `~/.epic/<network>`, so
where you run them from matters more than where the binary lives. That is the mechanism the next page
uses to run two wallets from one binary.
