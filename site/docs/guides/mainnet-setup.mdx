# Set up a node and wallet for mainnet

Mainnet is real value. Everything here assumes you have already done the local chain in
[run a local network](/guides/local-network) and [your first transfer](/guides/first-transfer), because
the mechanics are identical and the consequences are not.

Two processes. A node that validates and relays the chain, and a wallet that holds keys and asks the
node about the state of the world. You need a node. You do not need to mine.

## 1. Start the node {/* #1-start-the-node */}

Mainnet is the default network, so there is no flag:

```bash
epic
```

The node writes `epic-server.toml` on first run and reads it from then on. Editing that file is the
normal way to change behaviour, because most settings exist only as config keys, not as command-line
flags. Every key needs a restart.

Confirm it is up. The owner surface is authenticated and the secret is created for you:

<Tabs groupId="os">
<TabItem value="linux" label="Linux and macOS">

```bash
curl -s -u epic:$(cat ~/.epic/main/.api_secret) -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"get_status","params":[],"id":1}' \
  http://127.0.0.1:3413/v2/owner
```

</TabItem>
<TabItem value="win" label="Windows">

```powershell
$secret = (Get-Content "$HOME\.epic\main\.api_secret" -First 1).Trim()
$body = '{"jsonrpc":"2.0","method":"get_status","params":[],"id":1}'
Invoke-RestMethod -Uri 'http://127.0.0.1:3413/v2/owner' -Method Post `
  -ContentType 'application/json' -Body $body `
  -Authentication Basic -Credential (
    [PSCredential]::new('epic', (ConvertTo-SecureString $secret -AsPlainText -Force))
  ) -AllowUnencryptedAuthentication
```

</TabItem>
</Tabs>

The first sync downloads and validates the whole chain. Expect it to take a while and to use real disk.

### Ports {/* #ports */}

| Port | Purpose | Default binding |
| --- | --- | --- |
| <Ver k="ports.nodeApi" /> | HTTP API | `127.0.0.1` |
| <Ver k="ports.nodeP2p" /> | P2P | All interfaces |
| <Ver k="ports.stratum" /> | Stratum mining server | `127.0.0.1`, off by default |

Only the P2P port needs to be reachable from outside. Leave the API on loopback and read
[authentication and TLS](/api/authentication) before changing that. Every port and network offset is in
[the CLI reference](/reference/cli#ports).

### Sync validation settings {/* #sync-validation-settings */}

`skip_pow_validation` defaults to `true` and `disable_checkpoints` to `false`. Skipping proof of work
inside the checkpointed range is a sync speed optimisation rather than a weakened default: the skipped
range ends at a hardcoded checkpoint whose hash must match, and every header in it links back to that
checkpoint. Only the headers at the <Ver k="checkpointCount" /> checkpoint heights are compared by hash;
the ones between them are not.

| Where the block sits | Validation performed on mainnet |
| --- | --- |
| Inside the checkpointed range, up to height <Ver k="lastCheckpointHeight" /> | A header at a checkpoint height is compared against the hardcoded hash, and a mismatch aborts sync. Proof of work skipped while `skip_pow_validation` is `true` |
| Above the last checkpoint | **Full proof of work, always, whatever these settings say** |

A header batch counts as checkpointed only if every header in it does.

There are <Ver k="checkpointCount" /> checkpoints compiled into the node, in
<Src repo="node" path="chain/src/types.rs" line={432} />. The code is
<Fn repo="node" path="chain/src/chain.rs" line={1545} name="check_header_against_checkpoints" />, the
skip decision is <Fn repo="node" path="servers/src/common/adapters.rs" line={51} name="should_skip_pow" />,
and the node logs which policy applies when it starts on mainnet.

`disable_checkpoints` is ignored on mainnet. On a test network, with `skip_pow_validation` also `true`, it
extends the skipping past the last checkpoint for blocks more than <Ver k="powVerificationThreshold" />
below the tip
(<Fn repo="node" path="servers/src/common/adapters.rs" line={45} kind="const" name="POW_VERIFICATION_THRESHOLD" />).

Set `skip_pow_validation = false` to verify all historical proof of work yourself. That costs a much
longer initial sync.

### What the node stores {/* #what-the-node-stores */}

`chain_data`, the config file, log files and the API secret. `chain_data` is the large item and it is
disposable, so deleting it costs a resync and nothing else. A node holds no keys, so nothing in its data
directory needs backing up.

## 2. Create the wallet {/* #2-create-the-wallet */}

```bash
epic-wallet init
```

You will be asked to set a password and shown a recovery phrase.

:::danger[Write the recovery phrase down before continuing]

The phrase is the only thing that can reconstruct your funds. It is shown once here, and afterwards only
by `epic-wallet recover`, which needs the password.

:::

| Command | Effect |
| --- | --- |
| `epic-wallet init` | Create a wallet in the default location, `~/.epic/main` |
| `epic-wallet init -w` | Create it in the current directory. The flag takes no value |
| `epic-wallet init -r` | Restore from an existing recovery phrase |

`init -r` refuses to run if a seed file already exists, so restoring into a directory that already holds
a wallet means moving that wallet aside first. See
[back up and restore](/guides/backup-and-restore).

### Turn off the Tor listener {/* #turn-off-the-tor-listener */}

The wallet defaults `use_tor_listener` to `true` and expects a Tor binary that the release archives do
not ship, so `epic-wallet listen` starts a background thread that fails. Two ways to switch it off, and
one of them is per command:

```toml title="epic-wallet.toml"
[tor]
use_tor_listener = false
```

```bash
epic-wallet listen -n
```

`-n` is declared on `listen` only (<Src repo="wallet" path="src/cmd/wallet_args.rs" line={123} />), so it
has to be repeated on every `listen`. The config key applies to every command in that wallet directory
and is the setting to prefer. Neither affects Tor use by the node.

### What the wallet stores {/* #what-the-wallet-stores */}

[Back up and restore](/guides/backup-and-restore#what-to-back-up) lists every file in a wallet
directory, what it holds, and whether it needs backing up. The recovery phrase reconstructs your funds
but not your history. Transaction records, account labels and payment proof records live only in the
database and nothing on the chain can rebuild them.

### Ports the wallet opens {/* #ports-the-wallet-opens */}

`epic-wallet listen` opens the Foreign API on <Ver k="ports.walletForeign" /> and
`epic-wallet owner_api` opens the Owner API on <Ver k="ports.walletOwner" />. The Foreign port is derived
from the network; the Owner port is <Ver k="ports.walletOwner" /> on every network, so a second wallet on
the same machine collides there whatever chain it runs. Override `owner_api_listen_port`. Full list in
[the CLI reference](/reference/cli#ports).

## 3. Point the wallet at the node {/* #3-point-the-wallet-at-the-node */}

The wallet defaults to a node on loopback at port <Ver k="ports.nodeApi" />. Nothing to configure.

The wallet's calls go to node surfaces that need no credential, so moving either directory does not
break it. `node_api_secret_path` matters only for the Tor onion-address lookup; see
[the credential the wallet presents to the node](/api/authentication#the-credential-the-wallet-presents-to-the-node).
If you want a different node, set `check_node_api_http_addr` in `epic-wallet.toml`.

```bash
epic-wallet info
```

A balance of zero and no error means the wallet reached the node and the node answered. A 401 means the
node has a `foreign_api_secret_path` set, which epic-wallet <Ver k="wallet" /> cannot work with. Going by
the code, a node older than <Ver k="history.authChange" /> with an API secret would also answer 401; that pairing has
not been tested.

A wallet pointed at a public node works. That node sees which outputs the wallet asks about, and the
wallet does not validate the chain state it is given.
