# Set up a node and wallet for mainnet

Mainnet is real value. Everything here assumes you have already done the local chain in
[run a local network](/guides/local-network) and [your first transfer](/guides/first-transfer), because
the mechanics are identical and the consequences are not.

Two processes: a node that validates and relays the chain, and a wallet that holds keys and asks the
node about the state of the world. You need a node. You do not need to mine.

## 1. Start the node

Mainnet is the default network, so there is no flag:

```bash
epic
```

The node writes `epic-server.toml` on first run and reads it from then on. Editing that file is the
normal way to change behaviour: most settings exist only as config keys, not as command-line flags.
Every key needs a restart.

Confirm it is up. The owner surface is authenticated and the secret is created for you:

```bash
curl -s -u epic:$(cat ~/.epic/main/.api_secret) -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"get_status","params":[],"id":1}' \
  http://127.0.0.1:3413/v2/owner
```

The first sync downloads and validates the whole chain. Expect it to take a while and to use real disk.

### Ports

| Port | Purpose | Default binding |
| --- | --- | --- |
| <Ver k="ports.nodeApi" /> | HTTP API | `127.0.0.1` |
| <Ver k="ports.nodeP2p" /> | P2P | All interfaces |
| <Ver k="ports.stratum" /> | Stratum mining server | `127.0.0.1`, off by default |

Only the P2P port should be reachable from outside. Leave the API on loopback and read
[authentication and TLS](/api/authentication) before changing that.

### Sync validation settings

`skip_pow_validation` and `disable_checkpoints` both default to `true`. That is a sync speed
optimisation rather than a weakened default, and it is worth understanding rather than flipping.

| Where the block sits | Validation performed |
| --- | --- |
| Inside a checkpointed range | Header hash compared against a hardcoded checkpoint. A mismatch aborts sync. Proof of work skipped |
| Past the checkpoints, more than <Ver k="powVerificationThreshold" /> blocks behind the tip | Proof of work skipped |
| Within <Ver k="powVerificationThreshold" /> blocks of the tip | **Full proof of work, always, regardless of these settings** |

There are <Ver k="checkpointCount" /> checkpoints compiled into the node, in
<Src repo="node" path="chain/src/types.rs" line={432} />. Comparing a header against a known hash is a
stronger check than verifying its proof of work, so checkpointed history is not unverified, it is
verified differently. The code is
<Fn repo="node" path="chain/src/chain.rs" line={1567} name="check_header_against_checkpoints" />, the
skip decision is at <Src repo="node" path="servers/src/common/adapters.rs" line={728} />, and the floor
is <Fn repo="node" path="servers/src/common/adapters.rs" line={45} kind="const" name="POW_VERIFICATION_THRESHOLD" />.

Set both to `false` if you specifically want to verify all historical proof of work yourself. That is a
reasonable thing to want for an independent audit and it costs a much longer initial sync. It is not
required for a node you rely on day to day.

### What the node stores

`chain_data`, the config file, log files and the API secret. `chain_data` is the large item and it is
disposable: deleting it costs a resync and nothing else. A node holds no keys, so nothing in its data
directory needs backing up.

## 2. Create the wallet

```bash
epic-wallet init
```

You will be asked to set a password and shown a recovery phrase.

:::danger[Write the recovery phrase down before continuing]

The phrase is the only thing that can reconstruct your funds. It is not shown again without the
password, and nobody can recover it for you.

:::

| Command | Effect |
| --- | --- |
| `epic-wallet init` | Create a wallet in the default location, `~/.epic/main` |
| `epic-wallet init -w` | Create it in the current directory. The flag takes no value |
| `epic-wallet init -r` | Restore from an existing recovery phrase |

`init -r` refuses to run if a seed file already exists, so restoring into a directory that already holds
a wallet means moving that wallet aside first. See
[back up and restore](/guides/backup-and-restore).

### Turn the onion listener off

```toml title="epic-wallet.toml"
[tor]
use_tor_listener = false
```

The default is `true` and expects a binary the release archives do not ship, so a plain
`epic-wallet listen` can fail in a background thread. Either set this or pass `-n` on every `listen`.
Reasoning is in [what this version does not cover](/start#what-this-version-does-not-cover).

### What the wallet stores

| Item | Contents | Back up |
| --- | --- | --- |
| `wallet_data/wallet.seed` | Encrypted master key | **Yes. This is the wallet** |
| `wallet_data/db/sqlite/epic.db` | Output and transaction database | Yes. `scan` rebuilds outputs but not history |
| `wallet_data/saved_txs/` | Stored transaction objects | Yes, if you may need `repost` |
| `.owner_api_secret` | Owner listener credential | Regenerates harmlessly |
| `.api_secret` | The credential the wallet presents to the node | Must match the node's |
| Log file | Diagnostics. Off by default; set `log_to_file = true` | No |

The recovery phrase reconstructs your funds but not your history. Transaction records, account labels and
payment proof records live only in the database and nothing on the chain can rebuild them.

### Ports the wallet opens

| Port | Surface | Open when |
| --- | --- | --- |
| <Ver k="ports.walletForeign" /> | Foreign API, the listener | `epic-wallet listen` is running |
| <Ver k="ports.walletOwner" /> | Owner API | `epic-wallet owner_api` is running |

The Owner port does not shift per network, so a second wallet on the same machine collides there
whatever chain it runs. Override `owner_api_listen_port`.

## 3. Point the wallet at the node

The wallet defaults to `http://127.0.0.1:3413`, a node on the same machine, and in the default layout it
resolves the node's API secret to the same file the node created. Nothing to configure.

Two things change that. If you moved either directory, set `node_api_secret_path` to the node's
`.api_secret`. If you want a different node, set `check_node_api_http_addr` in `epic-wallet.toml`.

```bash
epic-wallet info
```

A balance of zero and no error means the wallet reached the node and the node answered. A 401 means the
two disagree about the secret.

:::note[On using someone else's public node]

It works, and it is a real trade. The node you query learns which outputs you ask about, and a wallet
cannot verify chain state it did not validate itself. For anything holding value worth the disk, run
your own.

:::
