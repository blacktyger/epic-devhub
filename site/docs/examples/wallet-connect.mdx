# Wallet: connect and read

Every Owner API v3 call travels inside an encrypted envelope. Getting that envelope right is the only
hard part of integrating Epic, and once you have it every other method is an ordinary JSON-RPC call.

Start the API:

```bash
epic-wallet owner_api
```

## What the handshake does

In words: your client generates a secp256k1 keypair, exchanges public keys with the wallet through
`init_secure_api`, multiplies to get a shared secret, and then wraps every subsequent JSON-RPC request in
`encrypted_request_v3`. The first wrapped call is `open_wallet`, which returns the token every later call
carries.

<HandshakeTrace />

### Where client implementations go wrong

Four things to get right, and each is a place implementations go wrong:

1. **The shared secret is the raw x coordinate** of the ECDH point, 32 bytes. It is **not** hashed.
2. **The cipher is AES-256-GCM** with a fresh 12-byte nonce per message, and the 16-byte auth tag is
   **appended to the ciphertext** before base64 encoding.
3. **The inner payload is a complete JSON-RPC request**, including `jsonrpc`, `id`, `method` and
   `params`, not just the params.
4. **Unwrap twice.** The outer response has an `Ok`/`Err` envelope, and so does the decrypted inner
   response.

### The Basic header these clients send

The clients below send an HTTP Basic header built from `~/.epic/main/.owner_api_secret`. On this
listener that header is not what authorizes the call, the `token` is, but sending it costs nothing and
keeps the client working against a listener that does check it. See
[authentication](/api/authentication).

:::warning[Do not use `SharedSecret::new` in Rust]

`secp256k1::ecdh::SharedSecret::new` applies SHA-256 to the point, which produces a different key and
every request will fail to decrypt. Epic uses the raw x coordinate, so use
`ecdh::shared_secret_point` and take the first 32 bytes.

:::

<TabItem value="sh" label="Shell">

There is no shell client for this surface, and that is a deliberate omission rather than a gap.

Reaching the first method call needs a secp256k1 keypair, an ECDH multiplication, and AES-256-GCM with a
per-message nonce. That is not something to assemble out of `openssl` invocations in a script, and a
half-correct implementation of it fails in ways that look like a wallet problem.

The node's JSON-RPC surface is a different matter, and [node queries](/examples/node-api) has a shell
client for it.

## Reading a balance

`retrieve_summary_info` returns a two-element array: whether the figures were validated against the
node, and the summary itself.

| Field | Meaning |
| --- | --- |
| `last_confirmed_height` | Height the figures are current as of |
| `total` | Everything the wallet knows about |
| `amount_currently_spendable` | What you can actually send right now |
| `amount_awaiting_confirmation` | Received but not yet deep enough |
| `amount_awaiting_finalization` | Part of a transfer still in progress |
| `amount_locked` | Reserved as inputs to a transfer you started |
| `amount_immature` | Coinbase outputs still inside the maturity window |

A gap between `total` and `amount_currently_spendable` is normal. See
[outputs and locking](/concepts/outputs-and-locking) for why, and
[stuck transactions](/guides/stuck-transactions) if it looks wrong.

:::note[Amounts are strings in JSON]

`u64` values are serialised as strings to survive JavaScript's number precision. Parse them as integers
before doing arithmetic, and divide by 100,000,000 for EPIC.

:::

## Listing outputs and transactions

Both calls return an object with a `pager`, not a bare array. This changed in wallet 4.0 and is the most
common thing to get wrong when porting a 3.x client. `limit`, `offset` and `sort_order` are optional in
the request, but supply them explicitly: without a limit a large wallet returns everything in one
response.

### Requesting a page

<Tabs groupId="lang">
<TabItem value="py" label="Python">

```python
result = wallet.call(
    "retrieve_outputs",
    {
        "token": wallet.token,
        "include_spent": False,
        "refresh_from_node": True,
        "tx_id": None,
        "limit": 100,
        "offset": 0,
        "sort_order": "desc",
    },
)

print(f"{result['pager']['records_read']} of {result['pager']['total_records']} outputs")
for entry in result["outputs"]:
    output = entry["output"]
    print(f"{output['status']:<12} {int(output['value']) / 1e8:>16.8f} EPIC  height {output['height']}")
```

</TabItem>
<TabItem value="js" label="JavaScript">

```js
const result = await wallet.call('retrieve_outputs', {
  token: wallet.token,
  include_spent: false,
  refresh_from_node: true,
  tx_id: null,
  limit: 100,
  offset: 0,
  sort_order: 'desc',
});

const epic = (freemen) => (Number(freemen) / 1e8).toFixed(8);
const {records_read, total_records} = result.pager;
console.log(`${records_read} of ${total_records} outputs`);

for (const {output} of result.outputs) {
  console.log(`${output.status.padEnd(12)} ${epic(output.value)} EPIC  height ${output.height}`);
}
```

### Validate account names before you pass them

:::warning[An unrecognised account name does not error]

Passing a `dest_acct_name` or account label the wallet does not know falls back to the default account
silently. Validate account names against `accounts` before using them.

:::
