# API authentication and TLS

Epic ships five HTTP surfaces. It protects the owner-facing ones with credentials and leaves the
foreign ones open because counterparties must reach them. TLS termination is left to the operator.

## The surfaces

| Surface | Default port | Credential | Who is meant to call it |
| --- | --- | --- | --- |
| Node `/v1/*` | <Ver k="ports.nodeApi" /> | Basic, `api_secret_path`, across the whole prefix | You, from the same machine |
| Node `/v2/owner` | <Ver k="ports.nodeApi" /> | Basic, `api_secret_path` | You, from the same machine |
| Node `/v2/foreign` | <Ver k="ports.nodeApi" /> | Optional Basic, `foreign_api_secret_path` | Anything that reads the chain |
| Wallet Owner `/v3/owner` | <Ver k="ports.walletOwner" /> | Token from `open_wallet` | You, from the same machine |
| Wallet Foreign `/v2/foreign` | <Ver k="ports.walletForeign" /> | None | A counterparty paying you |

The two Foreign surfaces take no credential by design: an interactive transfer needs the receiving
side reachable by a stranger. The wallet's Foreign API receives a slate, returns a partially signed
one, builds a coinbase for a miner configured to pay this wallet, and reports its version.

The node's `/v1` credential covers the whole prefix, including the chain reads that are open on
`/v2/foreign`. See [the v1 REST surface](/api/node#the-v1-rest-surface).

Both node surfaces read the same `api_secret_path` file, which the node creates on first run.

## Owner access on the wallet

Use `/v3/owner`.

```bash
# 1. establish the encrypted channel, 2. open the wallet, 3. call methods with the token
curl -d '{"jsonrpc":"2.0","method":"init_secure_api","params":{"ecdh_pubkey":"..."},"id":1}' \
  http://127.0.0.1:3420/v3/owner
```

Every method on `/v3/owner` takes a `token`, and a token comes from `open_wallet`, which needs the
wallet password. The wallet password is the credential for this surface.
`owner_api_listen_interface` defaults to `127.0.0.1`; for remote access, tunnel to loopback. The
listener is built at <Src repo="wallet" path="controller/src/controller.rs" line={143} />.

The full method list, and which calls move value, is on the
[wallet Owner API page](/api/wallet-owner).

## Basic authentication, where it applies

The node's `/v2/owner` uses HTTP Basic with the username literally `epic` and a secret file's contents
as the password:

```
Authorization: Basic base64("epic:" + <secret file contents>)
```

The node creates `~/.epic/<network>/.api_secret` on first run and points `api_secret_path` at it, so
this works without configuration:

```bash
curl -u epic:$(cat ~/.epic/main/.api_secret) \
  -d '{"jsonrpc":"2.0","method":"get_status","params":[],"id":1}' \
  http://127.0.0.1:3413/v2/owner
```

Secret files hold one 20-character random alphanumeric string with no trailing newline, and the
comparison is constant time. A rejected call returns 401 with a `WWW-Authenticate` header and a
JSON-RPC error body:

```json
{"jsonrpc": "2.0", "error": {"code": -32600, "message": "Unauthorized"}, "id": null}
```

Three behaviours:

- Commenting out `api_secret_path` removes the credential entirely. The generated config file invites
  it, and it is a reasonable thing to do on a private test chain.
- An empty `.api_secret` is regenerated with a new value rather than read as "no secret", so emptying
  the file does not switch authentication off.
- `OPTIONS` is passed through before the credential check, which is what makes CORS preflight work.

## Optional credential on the node's foreign surface

`foreign_api_secret_path` exists if you want the node's `/v2/foreign` to require a credential too.
Nothing creates the file for you and the default is a relative path, so the setting does nothing until
you create the secret and point at it absolutely:

```bash
head -c 40 /dev/urandom | base64 | tr -dc 'A-Za-z0-9' | head -c 20 > ~/.epic/main/.foreign_api_secret
```

```toml
[server]
foreign_api_secret_path = "/home/you/.epic/main/.foreign_api_secret"
```

The realm is `EpicForeignAPI` and the username is still `epic`. Because the default path resolves
against the node's working directory, whether it took effect depends on how the node was launched.
Verify with:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST http://127.0.0.1:3413/v2/foreign
# 401 once the secret is in place
```

## The credential the wallet presents to the node

`node_api_secret_path` points the other way: it is what the wallet sends when calling the node, and it
defaults to `<wallet dir>/.api_secret`. Left at defaults, node and wallet share `~/.epic/<network>/`
and resolve to the same file, so they agree with no configuration. Change the node's secret, move
either directory, or point the wallet at another node, and this is the key to update.

## TLS

Both binaries take the same pair, both commented out by default:

```toml
tls_certificate_file = "/path/to/fullchain.pem"
tls_certificate_key  = "/path/to/privkey.pem"
```

Setting the certificate switches the listener from HTTP to HTTPS. Setting it without the key is a
startup error. Certificates are read as a PEM chain; keys may be PKCS#1, PKCS#8 or SEC1 PEM. A file
that cannot be opened, cannot be parsed, or does not match its certificate stops the process rather
than falling back to HTTP, so a bad pair fails loudly at startup.

Self-signed certificates are documented as unsupported, which describes clients refusing to trust them
rather than a check in the server.

:::note[The bundled `epic client` does not speak HTTPS]

`epic client status`, `listconnectedpeers`, `ban` and `unban` build their URLs with a literal
`http://`, so enabling TLS on the node stops those subcommands working. Call the API with `curl`
instead.

:::

For most deployments a TLS-terminating reverse proxy in front of a loopback-bound listener is easier to
run than certificates inside the node, and it gives you one place to add authentication and rate
limits.
